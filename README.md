# Drop Anything

**English** | [简体中文](README.zh-CN.md)

Send files and text between devices on the same local network, right from the browser. No app, no sign-up. **Works on any LAN, including campus and corporate Wi-Fi that blocks multicast, where browsers normally can't connect to each other directly.**

- 📡 **Direct LAN transfer**: files and text go device-to-device over WebRTC, never through the server, at LAN speed.
- 🏫 **Works where multicast is blocked**: browsers hide local IPs behind mDNS (`xxx.local`) names, which need multicast to resolve. On campus or corporate networks that block multicast, tools like Snapdrop and PairDrop can't connect devices even on the same subnet. Here, "LAN direct mode" makes the browser use real local IPs.
- 🔍 **Only shows devices on your LAN**: devices are grouped by private subnet, not by public IP, so you don't see every stranger behind the same campus NAT.
- 🔐 **End-to-end encrypted pairing**: the server only sees a hash of the pairing code, so it can neither read nor forge signaling between paired devices.
- ☁️ **Server only does pairing**: deploy it for free on Cloudflare Workers, or on any VPS or Raspberry Pi. It needs almost no bandwidth.

> The UI is currently in Chinese. Button labels are given below in English, followed by the Chinese label.

## How it differs from Snapdrop / PairDrop

| | Snapdrop / PairDrop | Drop Anything |
|---|---|---|
| Discovery | Grouped by public IP. On a public deployment, everyone behind the same campus/office NAT sees each other, while devices using iCloud Private Relay or a VPN can't find each other | Grouped by private subnet. If public IPs differ, a peer is shown only after a direct LAN connection to it is verified |
| Networks that block multicast | No direct connection even on the same subnet; falls back to a TURN relay (slow, or fails) | Direct connection once LAN direct mode is enabled |
| Signaling security | Server relays plaintext signaling; PairDrop's pairing secret is generated by the server | Pairing code never leaves the devices; room signaling is end-to-end encrypted and authenticated |
| When a direct connection fails | Relays through TURN if configured | Shows why it failed, no relay by default; optional relay (`RELAY=1`) |

PairDrop has many more features (persistent pairing, translations, PWA, OS share sheet, etc.). If your network doesn't block multicast (most home routers), it's a great choice too.

## Usage

1. Open the same deployment URL in a browser on both devices.
2. **Same LAN**: on both devices, click **Enable LAN direct** (「开启局域网直连」) and allow camera access. The permission is only needed so the browser exposes local IPs; the camera is turned off immediately and nothing is captured. The other device then appears automatically, labeled **Same LAN** (「同一局域网」).
3. **To verify the other device with encryption, or if it doesn't show up**: on one device click **New room** (「新建房间」); on the other, enter the 8-character pairing code or scan the QR code. The card is then labeled **Same room · encrypted** (「同一房间 · 已加密」).
4. Click **Send file** (「发文件」) or **Send text** (「发文字」) on the other device's card, or drag files onto the card. Each transfer shows whether it went **direct** (「直连」) or through the **server relay** (「服务器中转」).

## Two ways to find each other

### Same LAN: enable LAN direct mode, devices appear automatically

Browsers replace local IPs in WebRTC with `xxx.local` names that must be resolved via multicast. When a campus network (e.g. NTU's NTUSECURE) blocks multicast, devices on the same subnet still can't connect. After **Enable LAN direct** is clicked and camera access is granted (and immediately released), the browser uses real local IPs:

1. Devices on the same subnet can connect directly (only one side needs to enable it).
2. The page derives all of the device's private subnets (`192.168.x.x` as /24, others as /16; e.g. a phone's Wi-Fi and cellular interfaces, or a laptop's wired and wireless ones, each count) and sends their hashes to the server. Devices sharing at least one subnet appear automatically (both sides need to enable it):
   - Same public IP as well: shown immediately.
   - Different public IP (iCloud Private Relay, VPN, proxy, or one side on IPv6): a direct connection is attempted in the background, and the device is shown only if the selected connection uses local addresses on both ends. Devices elsewhere that happen to use the same subnet can't reach your local address, so they never show up. Each device probes at most 8 such candidates.

On later visits, if camera permission is still granted, LAN direct mode is restored automatically without a prompt. The page must be served over HTTPS.

### Tested environments

| Network | Devices | Without LAN direct | Auto-discovery with LAN direct | Transfer with LAN direct |
|---|---|---|---|---|
| NTU campus Wi-Fi NTUSECURE (blocks multicast) | iPhone Safari ↔ Mac | ❌ No direct connection | ✅ (public IPs differed; shown after direct connection verified) | ✅ Direct both ways, files and text |
| Home router (Xiaomi) | iPhone Safari ↔ Mac | ✅ Direct (paired by code) | ✅ | ✅ Direct, fast |

Results from other networks and browsers are welcome.

### Different networks, or verifying the other device: pairing code

Click **New room** to generate an 8-character pairing code (e.g. `K7PM-Q3XD`); the other device enters it or scans the QR code. Note: if there's no network path between two segments (e.g. a device behind a dorm router and one on campus Wi-Fi), pairing still won't let them transfer unless relay is enabled (`RELAY=1`).

## Encryption and security boundaries

| What | Protection |
|---|---|
| Files and text | WebRTC DataChannel, DTLS-encrypted, only between the two devices |
| Device ↔ server connection | WSS (TLS) when deployed over HTTPS |
| Signaling within a room (SDP, ICE candidates) | End-to-end encrypted with an AES-256-GCM key derived from the pairing code; sender and receiver ids are bound as additional authenticated data |
| Relayed data within a room (only with `RELAY=1`) | Same as above, AES-GCM per frame |

How the pairing code is handled:

- The code only lives on the devices: in the input box, the QR code, or after `#` in the link. Browsers never send the part after `#` to the server, and the page removes it from the address bar once opened.
- PBKDF2-SHA256 (200,000 iterations) derives a 128-bit room id and a 256-bit AES key from the code. The server only receives the room id and cannot recover the code from it.
- There are 31⁸ ≈ 2⁴⁰ possible codes, so other users can't guess one. Even with a compromised server, brute-forcing a code would take about 10¹⁷ SHA-256 operations.
- Signaling from devices in the room must decrypt with the room key or it is dropped. The server therefore can't impersonate a peer or swap DTLS fingerprints to man-in-the-middle the connection.

Security boundaries:

- **Devices found only through LAN auto-discovery** share no secret, so their signaling is protected only by TLS and you have to trust the server (usually fine for a server you deploy yourself). For sensitive files, join the same room with a pairing code first; the card will show **Same room · encrypted**.
- Before a candidate with a different public IP is verified, both sides exchange connection info that includes local IPs. Devices elsewhere that happen to share your subnet (at most 8 per device) may therefore see your local IP, but they can't see your device or send you files.
- All devices in a room share one key. Click **Leave room** (「退出房间」) when done and use a new code next time.

## Running locally

```bash
npm install
npm start          # http://0.0.0.0:3000 by default
```

Pairing codes and LAN direct mode require a secure context: `localhost` works as is, while access via a LAN IP needs HTTPS. For quick local testing you can use a self-signed certificate:

```bash
mkdir -p certs && openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout certs/key.pem -out certs/cert.pem -subj "/CN=drop-anything-local" \
  -addext "subjectAltName=IP:$(ipconfig getifaddr en0),IP:127.0.0.1,DNS:localhost"
HTTPS_PORT=3443 npm start
```

With relay enabled (`RELAY=1`), you can append `?relay` to the URL while debugging so that files sent from that page skip the direct connection and go through the relay.

## Deployment

### Cloudflare Workers (free, recommended)

`cloudflare/` contains a Workers version of the pairing server. It speaks the same protocol as `server.js` and serves the same `public/` frontend. All connections are handled by a single Durable Object using the WebSocket Hibernation API, so it runs on the free plan, gets an HTTPS `*.workers.dev` domain, and never sleeps.

```bash
cd cloudflare
npm install
npx wrangler login    # log in to Cloudflare in the browser and authorize
npx wrangler deploy   # prints https://drop-anything.<your-subdomain>.workers.dev
```

Use `npx wrangler dev` for local development (http://localhost:8787 by default). Relay is disabled in the Workers version (`RELAY = "0"` in `wrangler.toml`); enabling it consumes request quota.

### VPS

The server only handles pairing, so the cheapest VPS is enough. With a domain and a real HTTPS certificate, no device sees certificate warnings and LAN direct mode works out of the box.

```bash
git clone <this repo> && cd drop-anything
npm install --omit=dev
PORT=3000 TRUST_PROXY=1 node server.js
```

Use `pm2 start server.js --name drop` or systemd to keep it running.

Caddy is recommended for automatic HTTPS. `/etc/caddy/Caddyfile`:

```
drop.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

Caddy handles WebSocket automatically. Always set `TRUST_PROXY=1` behind a reverse proxy, otherwise the server sees everyone as the same public IP.

nginx needs WebSocket enabled explicitly:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 3600s;
}
```

### Docker

```bash
docker build -t drop-anything .
docker run -d -p 3000:3000 -e TRUST_PROXY=1 drop-anything
```

Put an HTTPS reverse proxy in front of it (see above).

### Raspberry Pi (LAN only)

The server sees only private addresses, so it treats all clients as sharing one public IP and groups them by the subnets they report. Without a domain, use the self-signed certificate above and set `HTTPS_PORT`; every device has to trust the certificate manually the first time.

### (Optional) Relay and TURN

With `RELAY=1`, transfers fall back to relaying through the server's WebSocket when a direct connection fails; speed depends on the server's bandwidth. To relay over UDP instead, run coturn on the same machine and set:

```bash
TURN_URLS=turn:drop.example.com:3478 TURN_USERNAME=user TURN_CREDENTIAL=pass node server.js
```

## Environment variables

| Variable | Default | Description |
|---|---|---|
| `PORT` | `3000` | Listening port |
| `HOST` | `0.0.0.0` | Listening address |
| `RELAY` | off | Set to `1` to allow relaying file data through the server; when off, the server drops all relay data and only forwards signaling |
| `TRUST_PROXY` | off | Set to `1` to read the client IP from `X-Forwarded-For` |
| `HTTPS_PORT` | off | Additional HTTPS port (certificate read from `certs/key.pem` and `certs/cert.pem` by default; override with `TLS_KEY` / `TLS_CERT`) |
| `STUN_URLS` | Cloudflare + Google | Comma-separated |
| `TURN_URLS` / `TURN_USERNAME` / `TURN_CREDENTIAL` | none | Optional TURN server |

## Known limitations

- Received files are held in memory before saving, so multi-GB files may fail on phones.
- Subnets are approximated as /24 or /16 because browsers don't expose the netmask. Two different LANs behind the same public IP that use the same subnet (e.g. two Xiaomi routers with the default `192.168.31.x`) are treated as one LAN: devices see each other but can't connect.
- LAN direct mode needs camera permission. A device without a camera can't enable it; pair it by code instead, and let the other device enable LAN direct mode to establish the direct connection.
